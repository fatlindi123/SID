# SID backend

This directory contains the FastAPI backend. The API uses SQLAlchemy 2.0 with PostgreSQL and Alembic. Website exploration runs in asynchronous in-process worker tasks backed by PostgreSQL records; each task launches an isolated Playwright Chromium context. No AI behavior or generated test results are simulated.

## Requirements

- Python 3.11 or newer
- PostgreSQL 15 or newer
- A PostgreSQL database and role with permission to create or alter tables

The runtime dependencies are in requirements.txt. Test-only dependencies are in requirements-dev.txt.

## Local setup

From this directory, create a virtual environment and install the dependencies:

    py -3.11 -m venv .venv
    .\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
    $env:PLAYWRIGHT_BROWSERS_PATH = ".cache/playwright"
    .\.venv\Scripts\python.exe -m playwright install chromium

Copy .env.example to .env and replace the DATABASE_URL username and password placeholders with a PostgreSQL role and password available in your environment:

    postgresql+psycopg://USER:PASSWORD@localhost:5432/software_intelligence

URL-encode reserved characters in credentials. If your PostgreSQL server uses local trust or peer authentication, you may instead omit credentials as supported by that server. Do not commit .env or real credentials.

The application loads `backend/.env` independent of the current working directory. Environment variables override values in the file. `APP_ENVIRONMENT` accepts `development` or `production`. `CORS_ORIGINS` is a JSON array and defaults to empty. For local development, copy the development origins from `.env.example`; in production, only explicit HTTPS origins are accepted, and localhost, loopback addresses, and wildcard origins are rejected. The API does not enable credentialed CORS.

## Database and migrations

Create the software_intelligence database and grant the configured role permission to use it. Then, from the backend directory, apply the initial schema:

    .\.venv\Scripts\alembic.exe upgrade head

The initial migration creates the projects table. Migration 0002 adds explorations, discovered pages, observed interface elements, and exploration events. Apply the current schema with:

    .\.venv\Scripts\alembic.exe upgrade head

To inspect migration state:

    .\.venv\Scripts\alembic.exe current
    .\.venv\Scripts\alembic.exe history

To generate a later migration after changing SQLAlchemy models:

    .\.venv\Scripts\alembic.exe revision --autogenerate -m "describe the schema change"

Review autogenerated migrations before applying them.

## Run the API

From the backend directory:

    .\.venv\Scripts\uvicorn.exe app.main:app --reload --host 127.0.0.1 --port 8000

The health endpoint is GET http://127.0.0.1:8000/api/v1/health. It executes SELECT 1 using the configured PostgreSQL connection and returns HTTP 200 only when the database is reachable. A database failure returns HTTP 503 with a structured error body.

GET /api/v1/system/status returns the application version and environment plus safe status values for PostgreSQL, AI provider configuration, and the Playwright Chromium runtime. It never returns provider URLs, model names, API keys, database URLs, or credentials. AI status means the endpoint and model are configured; it does not verify provider connectivity. Chromium status checks the installed executable without launching a browser.

The exploration API is available under /api/v1/explorations:

- POST /api/v1/explorations accepts {"url": "https://example.com"} and immediately returns a queued exploration.
- GET /api/v1/explorations lists recent explorations.
- GET /api/v1/explorations/{id} returns live state and discovered counts.
- POST /api/v1/explorations/{id}/cancel cancels a queued or active exploration.
- GET /api/v1/explorations/{id}/pages returns saved page metadata, DOM outlines, screenshots links, and observed elements.
- GET /api/v1/explorations/{id}/events returns ordered progress events.

Interactive API documentation is available at /docs.

The worker accepts only public HTTP and HTTPS targets. It resolves and checks every target and browser request, routes Chromium through a loopback-only egress proxy that connects to the validated IP address, blocks private or reserved IP space, prevents cross-origin page navigation, and blocks non-GET/HEAD requests. The static crawl does not activate controls. After saving a page, interaction discovery may probe only explicit non-form tabs and disclosure buttons; it excludes links, form-associated controls, submit/reset controls, ambiguous controls, and unsafe labels. Exploration is limited by EXPLORATION_MAX_PAGES, EXPLORATION_MAX_DEPTH, and EXPLORATION_PAGE_TIMEOUT_SECONDS (defaults: 20 pages, depth 3, 30 seconds per page).

The queue is in-process, with job state and results persisted in PostgreSQL. The browser work runs asynchronously in worker tasks and never holds the create request open. A backend restart requeues unfinished explorations. Run one API process; multiple independently started API processes can each recover queued work. No separate worker process is required.

## AI analysis

AI analysis uses an optional OpenAI-compatible chat completions endpoint. Configure `AI_API_BASE_URL` and `AI_MODEL` in `backend/.env`; configure `AI_API_KEY` only when the selected endpoint requires it. This works with a local compatible model endpoint as well as a hosted provider. No provider or key is enabled by default, and no provider dependency is installed. The endpoint must support JSON object responses. Set `AI_REQUEST_TIMEOUT_SECONDS`, `AI_ANALYSIS_WORKER_CONCURRENCY`, and `AI_MAX_CONTEXT_ELEMENTS` to tune request limits.

Only saved page metadata and persisted DOM element metadata are sent for analysis. Screenshots, cookies, and form values are excluded. Analysis output is schema-validated and evidence references must point to saved pages and elements. Forms and fields are listed from stored DOM elements; because the crawler does not persist DOM parent relationships, fields are grouped by page rather than asserted to belong to a particular form. Suggested scenarios remain unexecuted until an operator starts one from the Test Cases section.

The API exposes `POST /api/v1/explorations/{id}/analysis` to queue or rerun analysis, `GET /api/v1/explorations/{id}/analysis` for current status, and `GET /api/v1/explorations/{id}/analysis/results` for completed structured results. One result row is reused per exploration on rerun. An unset provider produces a persisted failed status with configuration guidance.

## Browser test execution

Test execution reuses the existing Chromium setup, URL validation, and safe egress proxy used by browser exploration. Apply migrations with `alembic upgrade head`; `0004_test_execution` adds test runs and steps, `0005_interaction_observations` adds safe interaction observations, `0006_persistent_test_cases` adds persistent test cases and an optional case reference on runs, and `0007_test_case_management` adds editable case metadata, soft deletion, and nullable analysis associations for user-created cases. These migrations are additive and preserve existing exploration, analysis, interaction, and test-run records.

The configured PostgreSQL role does not have `REFERENCES` permission on the existing exploration and analysis tables. Test cases therefore store their exploration and source-analysis UUIDs without foreign keys, and the API and worker validate those relationships. The migration adds a nullable `test_runs.test_case_id` foreign key to the new `test_cases` table; it remains nullable so historical runs are preserved.

- `GET /api/v1/explorations/{id}/test-cases` lists persisted cases. It accepts `source`, `status`, `search`, `limit`, and `offset`; status is `active`, `superseded`, `deleted`, or `all`. The response includes filtered totals and the AI analysis state (`not_started`, `queued`, `running`, `completed`, or `failed`). Completed analyses are synchronized idempotently on read; incomplete or failed analyses are not treated as empty completed results.
- `POST /api/v1/explorations/{id}/test-cases` creates a user-owned workflow from saved page/element evidence. `PATCH /api/v1/explorations/{id}/test-cases/{case_id}` edits its name, description, and validated workflow definition. AI scenario definitions remain read-only, although their metadata can be edited.
- `POST /api/v1/explorations/{id}/test-cases/{case_id}/duplicate` creates an independently identified user-owned copy. `DELETE /api/v1/explorations/{id}/test-cases/{case_id}` soft-deletes a case and preserves all associated runs and steps.
- `POST /api/v1/explorations/{id}/test-cases/{case_id}/runs` creates a run from the case's current validated definition. A user-created case does not require an AI analysis. The worker always uses the persisted run snapshot.
- `POST /api/v1/explorations/{id}/test-runs` accepts `{"test_case_id": "<uuid>"}` and queues that saved case. The existing evidence-backed manual SauceDemo smoke-test request remains supported and creates/reuses a `user_created` case.
- `GET /api/v1/explorations/{id}/test-scenarios` remains available for compatibility with older clients; new clients should use persisted test cases.
- `GET /api/v1/explorations/{id}/test-runs` is a compatibility list of persisted run and step results, bounded to 100 rows with `limit` and `offset`; new clients should use the paginated history endpoint.
- `GET /api/v1/explorations/{id}/test-run-history` returns stable paginated history, optionally filtered by `test_case_id`, and an exploration-wide active-run count.
- `GET /api/v1/explorations/{id}/test-runs/{run_id}` retrieves one run.
- `POST /api/v1/explorations/{id}/test-runs/{run_id}/cancel` cancels a pending or running run.

AI cases receive deterministic UUIDs from the exploration, source, and logical scenario identity rather than an array position. Analysis and scenario hashes make source and definition versions explicit. A changed definition updates the current logical case while every `TestRun` retains its own scenario and step snapshot; workers validate and execute that saved run snapshot without recompiling the current analysis or case. Existing runs keep a null `test_case_id` and remain readable/executable through their legacy snapshots. Deleted cases are retained as rows with `deleted_at`; no historical run or step is removed.

The initial action set is intentionally limited to navigating to an already saved page, clicking an evidenced same-origin link whose destination is also saved, and asserting that one evidenced element is visible. Selectors come from persisted crawler output and must match a restrictive CSS locator allowlist. The worker blocks non-GET/HEAD requests, cross-origin page navigations, unsaved destinations, and paths associated with destructive actions. It does not fill or submit forms, execute generated JavaScript, or use model text as a selector. The compatibility `test-scenarios` endpoint can still report unsupported workflows; only validated persisted cases can be queued. Each step's status, duration, error, and observed URL/title/element evidence are saved in PostgreSQL.

Runs are processed by a single in-process worker queue. Pending runs recover after restart; a run interrupted after it began is marked failed and is not replayed, because a browser action may already have occurred. The UI loads run history from the API, so saved results remain after refresh.

## Safe interaction discovery

The existing exploration worker runs bounded interaction probes after it saves each page. Each probe uses a fresh Chromium context behind the same safe egress proxy and URL validator. The request guard permits only validated GET/HEAD traffic and the saved page as the only navigation target. Unsafe request paths and non-read-only methods are blocked; any block makes that observation `blocked`, never `observed`. After each probe, a separate clean context reloads the page and compares bounded page-state evidence to the original baseline. If restoration cannot be verified, the worker stops probing that page.

Only explicit tabs inside a tablist and buttons with `aria-expanded` plus valid `aria-controls` are eligible. Form controls, links, submit/reset controls, unclear controls, disabled controls, and unsafe/sensitive labels are skipped. Observations capture a URL without query/fragment data, a bounded title and accessible role/name, expanded/selected state, and a bounded diff of visible semantic elements. Form controls and their descendants are omitted; cookies, input values, credentials, HTML, and page screenshots are not copied into interaction evidence. Per-page and per-exploration limits are configured by `INTERACTION_PROBE_TIMEOUT_SECONDS`, `INTERACTION_MAX_PROBES_PER_PAGE`, `INTERACTION_MAX_PROBES_PER_EXPLORATION`, `INTERACTION_MAX_OBSERVATIONS_PER_EXPLORATION`, and `INTERACTION_MAX_CANDIDATES_PER_PAGE`.

- `GET /api/v1/explorations/{id}/interactions` returns saved observations, with optional `page_id` and a bounded `limit`.
- Each record has one of `observed`, `skipped`, `blocked`, or `failed`; a unique exploration/page/probe key makes terminal persistence idempotent.
- The dashboard's Interactions tab reads the saved records from the API, including after refresh.

The current PostgreSQL role cannot add `REFERENCES` permissions to the existing exploration tables, so the additive observation table stores the exploration and page UUIDs without foreign keys. The API verifies that a requested page belongs to the requested exploration before returning filtered results. Backend fixture tests exercise actual Chromium behavior, request blocking, cancellation, timeouts, and restoration failure.

## Workflow Intelligence

Workflow discovery uses only persisted records. It creates separate candidates for safe captured links between saved pages, eligible `observed` tab/disclosure observations, and current test cases that still compile against saved evidence. A captured link is labeled **suggested** because the crawler recorded the link and target page but did not record a click; an interaction observation is labeled **observed** and remains a single isolated transition. AI-derived test cases remain **suggested**, and discovery does not execute or rerun any case.

The additive `0010_workflow_intelligence` migration adds `workflows` and ordered `workflow_steps` sidecar tables. IDs are deterministic from exploration and source IDs. Rebuilds update generated rows by source hash, mark missing or invalid sources stale, preserve manual workflows and user-edited names/descriptions, and clear review only when source evidence changes. Project associations are validated and mirrored at the application layer because the existing database role does not have general `REFERENCES` privileges.

- `GET /api/v1/explorations/{id}/workflows` and `GET /api/v1/projects/{id}/workflows` list scoped workflows with search, provenance/status filters, and offset pagination.
- `GET .../workflows/{workflow_id}` retrieves ordered steps and evidence.
- `PATCH .../workflows/{workflow_id}` edits only the workflow name and description; evidence references are read-only.
- `POST .../workflows/{workflow_id}/review` marks a workflow reviewed.
- `POST /api/v1/explorations/{id}/workflows/rebuild` and `POST /api/v1/projects/{id}/workflows/rebuild` synchronize generated candidates from saved data. Archived projects reject rebuilds; incomplete project explorations are skipped.

Discovery never launches Chromium, submits forms, follows links, sends AI requests, or marks a test as passed. A source that no longer validates against its saved page/element/observation evidence is omitted and its prior generated workflow is marked stale.

## Reports

Migration `0011_reports` adds an independent `reports` table. Every generation creates a new row with its requested scope, timezone-aware generation/completion timestamps, run-date filters, status, and an immutable JSON snapshot. Project and exploration IDs are checked by the report service because this PostgreSQL role cannot add foreign keys to the existing source tables. Archived projects can be reported as historical data; report generation does not change project, exploration, workflow, test-case, or run records.

- `POST /api/v1/reports/explorations/{id}` generates a report from one saved exploration.
- `POST /api/v1/reports/projects/{id}` generates a report from only the explorations explicitly assigned to that project.
- `GET /api/v1/reports` returns paginated metadata and filters by type, project, exploration, and generation date. It omits snapshots to keep history responses bounded.
- `GET /api/v1/reports/{report_id}` reads the saved snapshot; opening it never regenerates from current source data.
- `GET /api/v1/reports/{report_id}/export.json`, `/print`, and `/export.pdf` export the same saved snapshot. PDF rendering uses the existing Playwright Chromium dependency against local, sanitized HTML; it does not navigate to a website or make external requests.

Reports use saved exploration, page, element, event, analysis, interaction observation, graph node/edge, workflow/step, test case, test run/step, project metadata, and explicit project-exploration association rows. The JSON snapshot records source UUIDs and precise metric definitions. Missing, stale, or partial evidence is called out; suggested workflows are kept separate from observed or user-authored workflows and are never counted as verified journeys. The optional run-date window applies only to test-run history and latest-run-per-case classifications; other saved scope sections are not date-filtered. Browser session data, raw HTML, screenshot blobs, form values, run action payloads, and raw error details are not included.

Install the browser binary for PDF rendering using the same local Playwright setup used by the backend:

    $env:PLAYWRIGHT_BROWSERS_PATH = ".cache/playwright"
    .\.venv\Scripts\python.exe -m playwright install chromium

The Reports workspace reads report history from the API, opens the stored snapshot, and provides PDF, JSON, and print actions. It does not generate reports automatically on page load.

Screenshots are stored as JPEG blobs in PostgreSQL and served through the page screenshot endpoint. Visible text, accessible names, labels, and selected non-value attributes are persisted. Form values, cookies, and authentication credentials are not captured.

Set VITE_API_BASE_URL in the frontend environment if the backend API is not available at http://127.0.0.1:8000/api/v1.

Application request logs are JSON lines written to standard output. Each request receives an X-Request-ID response header, also included in its application logs.

## Tests

From the backend directory:

    .\.venv\Scripts\python.exe -m pytest --basetemp=.pytest-tmp

The API and service tests use an isolated in-memory SQLite database. Browser tests use controlled local fixtures and do not visit external websites. The migration test applies Alembic to a temporary SQLite database to verify migration wiring without requiring a running PostgreSQL server. To verify PostgreSQL itself, configure `DATABASE_URL` for a real local database, then run `alembic upgrade head`, `alembic current`, and request the health endpoint. `GET /api/v1/health` checks the API process and database connection; it does not report per-task queue depth.

## Authentication and account isolation

Migration `0012_authentication` adds account, hashed server-session, challenge, first-account bootstrap, and workspace ownership sidecar tables. Migration `0013_first_login_onboarding` adds a nullable server-side completion timestamp; accounts that existed before the welcome experience are marked complete, and new accounts are sent to `/welcome` after their first successful sign-in. Migration `0014_remove_google_identity` removes the unused Google identity column after confirming no accounts are linked to it; it preserves historical OAuth challenge rows. Completing the welcome screen calls `POST /api/v1/auth/onboarding/complete`, which is authenticated, CSRF protected, and idempotent. These revisions append to migration history without editing earlier files. Run `alembic upgrade head` before starting this version.

Sign-in uses email and password accounts. Registration accepts any syntactically valid email address, stores a directly chosen password using Argon2, and signs the account in immediately; the mailbox is not verified. Choose an address you control if you may need password recovery. Recovery links require configured email delivery, are one-use, and expire. Authentication cookies are HttpOnly and SameSite=Lax, and Secure in production. Mutating requests require both the server-issued CSRF token and an allowed Origin. The frontend keeps the CSRF token in memory only and never receives session tokens.

Existing unowned workspace rows are claimed atomically by the first account created. New accounts do not receive another account's rows. The API scopes workspace reads and writes to the authenticated owner. Foreign keys are not added to legacy workspace tables because of the configured PostgreSQL role's limitations; ownership is checked in the application layer.

Authentication endpoints are under `/api/v1/auth`: `GET /configuration`, `GET /csrf`, `POST /register`, `POST /login`, `GET/PATCH /me`, `POST /onboarding/complete`, `POST /logout`, `POST /forgot-password`, and `POST /reset-password`. The legacy `POST /verify-email` endpoint remains for any historical verification challenges; new registrations do not create them. Public configuration reports only whether password recovery email delivery is available. The account menu uses the real `/me` response and supports profile name edits and logout.

Authentication-attempt throttling is in-process and resets on restart. It is not a deployment-wide API rate limiter; deploy behind a trusted network boundary and add shared abuse controls before scaling or public exposure. SMTP delivery must be verified in the target environment; local automated tests do not establish external email delivery.

## Deployment and recovery preparation

There is no Dockerfile, Compose file, process supervisor configuration, CI workflow, or live deployment target in this repository. Run migrations explicitly with `alembic upgrade head` before starting the API. Start exactly one API process for the current in-process exploration, analysis, and test execution queues. Do not use multiple Uvicorn workers or replicas: each process would own separate queues and could recover the same pending work. Pending jobs are durable in PostgreSQL and requeued at startup. A running test run interrupted by shutdown is marked failed and is not replayed. Use a process manager with graceful shutdown and enough termination time for active exploration tasks to persist their stop state.

For Linux, install the Playwright browser and operating-system libraries in the same deployment image/environment as the API:

    python -m playwright install --with-deps chromium

Set `PLAYWRIGHT_BROWSERS_PATH` to that installed location at runtime, and verify both controlled Chromium tests and PDF export before release. The ignored local `backend/.cache/playwright` directory is not a deployment artifact and must not be assumed to exist on a new host. The PDF renderer uses local sanitized HTML and blocks all page network requests.

Set `APP_ENVIRONMENT=production` and an explicit `DATABASE_URL`; the development localhost database default is rejected in production. Set `CORS_ORIGINS` to the frontend's exact HTTPS origin, or to `[]` for same-origin hosting. Configure `FRONTEND_BASE_URL` and working SMTP settings if email registration and recovery are enabled. If AI is enabled, its provider URL must use HTTPS. Set the frontend `VITE_API_BASE_URL` at build time to the deployed HTTPS API URL. TLS termination and deployment-wide abuse controls remain operational requirements.

PostgreSQL is the durable store for explorations, browser evidence, analysis, test cases/runs, interaction observations, graph/workflow records, and reports. Back up with PostgreSQL's supported backup tools (for example, `pg_dump -Fc`). Store backups with restricted access and rehearse restore into a separate database before relying on them. Browser binaries and Python virtual environments can be recreated; they are not backups. Preserve the database and the configured PostgreSQL role's schema privileges during upgrades. The current application-level relationship checks exist because the configured role cannot add foreign keys to several legacy source tables.

Workspace APIs enforce authenticated owner scoping, and authentication routes use process-local throttling. There is no deployment-wide API rate limiter. At minimum, deployments need a network boundary, monitoring, and an explicit queue strategy before scaling beyond one API process. This repository contains no deployment-level evidence, so passing local tests does not establish production readiness.
